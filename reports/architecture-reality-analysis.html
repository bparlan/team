Shape is sound. Provenance is not. Every architectural relationship the diagrams assert — all 13 edges — is real and verified against the source. Every module ARCHITECTURE.md assigns exists, and all 20 core/ modules have a live or correctly-documented importer story. What has decayed is traceability: line-number citations, content anchors, and the gate that should catch either drifting.

1. Method

Three independent measurements, so the numbers are comparable to ARCHITECTURE.md §5.2.1's own claim of having used "an AST scan for imports at any nesting level plus a runtime sys.modules check across all three entry points."

  • AST import scan — 97 modules, 155 in-package edges, imports at any nesting level.
  • Runtime sys.modules — what import theteam actually loads, plus every lazy re-export resolved.
  • Symbol resolution — each cited file:line checked against the real def/class line, and each cited file's blob hash against git hash-object.

The architecture gate was run, not assumed: bash scripts/check_invariants.sh → PASSED (7 checks). scripts/check_import_graph.py → 88 modules (budget 90), 7 of 7 theteam.core.* (budget 8), no cluster tier. Suite: 800 passed.

3. Anchors — the mechanism that should have caught this, and does not

diagrams/active-usage-architecture.anchors.json records a content hash for each of the 14 cited files, plus the revision it was generated from.

All 14 hashes have drifted. Anchored at ca3673bf; HEAD is 02b8b76. Not one cited file still matches.

The anchor records whole-file hashes, so it is a change detector, not a citation checker — any edit anywhere trips it, and it says nothing about whether line 604 still holds build_parser. It is a coarser instrument than the thing it was meant to protect, and nothing runs it.

Consequence: the file that exists precisely to detect architectural drift is itself undetectable drift, because no script reads it. scripts/check_invariants.sh has 7 checks; none touches diagrams/. There is no prompt-truth-style gate for diagrams, which is the same gap that plan closed for prompts.

4. Where the code contradicts the document

4.1 Layer 0 contract is violated by the CLI — defect

ARCHITECTURE.md:459 defines Layer 0 (Entry) as owning "argument parsing, exit codes, JSON output" and requiring it "must not know about any domain object."

theteam/cli.py references six domain symbols directly: TaskRepository, TaskExecutor, TaskScheduler, StateStore, CircuitBreaker, run_discussion.

Reason — the doc describes an intent that was never completed. §2.3 shows the pattern being applied where it mattered: run_due_tasks() was "extracted out of cmd_run rather than duplicated into serve" precisely so the scheduler would not import the CLI. The same discipline was never applied to the other 11 commands. Layer 0 is an aspiration in §5.1 and a description of practice nowhere else. This is the same class as the health_monitor.py finding at §5.2.1 — documented honestly, but recorded as "open work" rather than as a contract breach.

4.2 import theteam contradicts its own comment — stale

theteam/__init__.py:30-33 states that importing theteam.core.state_manager "loads database, which loads the PostgreSQL cluster/wal/transaction modules", so every import theteam pulled a database tier §5.1 never placed in the stack.

Measured sys.modules after a bare import theteam: database is loaded — but postgres_cluster is not. The chain stops one link short of what the comment claims.

Reason: database.py now imports postgres_cluster at point of use rather than module scope — which is exactly the fix §5.2.1 describes ("Imported at point of use by database.py"). The comment documenting the defect was never updated to record that the defect is fixed. The comment is correct about the past and wrong about the present, and it is the first thing a reader meets when reasoning about the import graph.

4.3 Two packages are empty and tracked — orphan

theteam/skill/ and theteam/automation/ contain no files and are tracked. theteam/skill/ is the residue of skill/SKILL_metadata.py, deleted in M10. Neither is named in §5.2. §5.3.1 tracks one orphaned directory (config/routine-engine/) as "not removed, with the reason" — these two have no such entry.

Reason: M10's deletion pass removed files, not the directories they emptied. The cost is low but the precedent matters: §5.3.1's rule is "an orphan is recorded with a reason," and these are unrecorded.

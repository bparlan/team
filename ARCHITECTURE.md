# Part 1 — The Product

## 1.1 What it does

`theteam` puts a small panel of expert reviewers in your working session and keeps your scheduled project tasks running.

Two capabilities:

**Commentary.** A roster of specialists watches your session and speaks when there is something to say. They read your real session, not a guess at it. They are individually addressable. They do not speak when they have nothing to add.

**Tasks.** Tasks live in plain YAML files you can read and edit. A single `theteam run` executes whatever is due. Every execution is bounded, isolated, audited, and reversible.

## 1.2 What you can rely on

These are the product's promises. Each is a test.

| Promise | You can check it by |
|---|---|
| The team reads your real session | `theteam comment status` reports the `last_digest` the commentary controller last saw, and a tick over a missing session reports `{spoke: false, reason: "no_session"}` |
| The team is silent rather than filler | Every tick reports `spoke: false` with a reason, or up to 2 opinions. Never a third. |
| Opinions are never invented | Running `theteam discuss` outside OMP **fails with an error naming the command to run inside OMP.** It never returns an opinion. |
| Tasks cannot run away | Every phase has a mandatory memory bound. A phase that exceeds it is killed and reported, not left running. |
| A failing task stops burning cycles | A task failing repeatedly trips a circuit breaker. `theteam tasks` shows the trip. |
| Nothing changes unrecorded | Every task create, edit, delete, and execution is in a hash-chained audit log. `theteam status` verifies the chain. |
| Your tasks are yours | Tasks are YAML in your repo. `theteam run` holds no state you cannot delete. |

## 1.3 The four requirements, mapped

| You said | It is |
|---|---|
| Bootstrap into any project | `theteam bootstrap` — M1 |
| In-context team commentary | `theteam comment` — M5 |
| Create, edit, delete tasks | `theteam task create\|edit\|delete` — M3 |
| Loop and manage tasks | `theteam loop` to schedule, `theteam run` to execute now, `theteam serve` to execute on an interval — M2, M4, M10. M10 made `serve` actually schedule; see §2.3. |

# Part 2 — The Command Surface

Commands are named for what the user wants, not for the internal mechanism. `theteam run` runs due tasks. It is not called `loop tick`, because "loop" is an implementation detail and "tick" is a unit of time the user does not control.

```
theteam bootstrap [path]               generate a team for this project
theteam status                        trust surface — see §3
theteam discuss <topic>               one-shot team discussion, this turn only
theteam serve                         metrics endpoint
theteam loop <task_id>                schedule one registered task on an interval
theteam tasks                         list every task and its state
theteam run                           execute everything currently due
theteam history                       per-task success rate, last run, last failure
theteam task create|edit|delete|show  single-task operations
theteam comment on|off|status         continuous in-context commentary
theteam watch status|tasks|history    the trust surface, rendered, in the terminal
theteam manager                      grow the roster from a topic
```

Twelve subcommands. The list is the whole surface; nothing else is declared.

| Command | Arguments and flags | Output you can predict |
|---|---|---|
| `bootstrap [path]` | `--interactive`, `--json` | `{ok, config, state_dir}` in JSON; the config path and state directory as text. Non-interactive unless `--interactive`. |
| `status` | `--json` | Roster, state directory, task counts, breaker trips, audit-chain state. |
| `discuss <topic>` | `--json` | The synthesized verdict — or, outside OMP, `{ok: false, error: ...}` naming the command to run inside OMP. Never an invented opinion. |
| `serve` | `--port N` (default `$THETEAM_METRICS_PORT`, else 8000), `--tick-seconds S` (default `$THETEAM_TICK_SECONDS`, else 60), `--json` | Runs due tasks on an interval and serves Prometheus `/metrics` and `/health`. **M10 changed this command**: it used to bind metrics to a `UnifiedLoop` whose only task producer had no caller, so every counter read `0.0` forever. It now sweeps the same due tasks `theteam run` executes, so `/metrics` reports work that actually ran. |
| `loop <task_id>` | `--interval N` minutes (default 60), `--json` | `{task_id, interval_minutes, next_run}`. An unknown task id is a named failure, not a silent no-op. |
| `tasks` | `--json` | One row per task: `id`, `order`, `next_run`, `last_result`, `breaker`, `breaker_consecutive_failures`. |
| `run` | `--only <id>`, `--json` | `{ran, skipped, failures, results}`. Idempotent: with nothing due it is `{ran: 0}` twice, identically. |
| `history` | `--task <id>`, `--json` | Per task: `runs`, `successes`, `failures`, `success_rate`, `last_run`, `last_result`, `last_failure`, `breaker`, `consecutive_failures`. |
| `task create` | `--path <file.yaml>` (**required**), `--json` | The created task as stored. Invalid definitions are rejected at write time. |
| `task edit <task_id>` | `--patch <file>` (**required**), `--json` | The new task state. Refuses orphaning a schedule. |
| `task delete <task_id>` | `--yes`, `--json` | Without `--yes`, the deletion plan. With it, what was removed. |
| `task show <task_id>` | `--json` | The task exactly as stored. |
| `comment on` | `--max-members N` (default 3, hard cap 4), `--json` | `{ok, on, max_members, marker}`. Above the cap is **refused with a named reason, not clamped** — silently clamping would hide a caller bug behind a success. |
| `comment off` | `--json` | `{ok, on, sentinel}`. Writes the stop sentinel, so a controller mid-tick still sees it. |
| `comment status` | `--json` | `{on, marker, max_members, last_digest, last_opinion, tick_count}`. |
| `watch <status\|tasks\|history>` | `--once`, `--interval SECONDS` (default 5), `--monitor`, `--json` | The same payload the view reads, rendered as a frame. `--once` prints one frame and exits. Unmeasured cells read `-` or `never run`, never `0`/`closed`/`intact`. `--monitor` adds a change block; see below. |
| `manager` | `--topic`, `--status`, `--reset`, `--apply`, `--json` | `--topic` proposes and writes nothing; `--apply` persists. `--status` states why every member is on the roster, and reports any it cannot justify. `--reset` restores the bootstrapped team. |
| global | `--project-root PATH` (default `$THETEAM_PROJECT_ROOT`, else `$PWD`), `--json` | Applies to every command. |

> **`run` returns 1 when a task failed** (M9 Phase 4). It previously returned 0 with
> `failures: N` in the payload, so a shell could not distinguish a red suite from a green
> one without parsing JSON. §2.1 already names this: `1` means "the command exists and
> failed". Two consecutive `run` calls with nothing due still return 0, so the §7.1.4
> idempotence check is unaffected.
>
> **`run --only <id>` means "run this one now"** and bypasses the schedule (M9 Phase 4).
> It previously filtered the *due* set, so naming a task that had never been scheduled
> reported `nothing due` — which made every `runner: llm` task inert on a project where
> the user had never run `theteam loop`. A schedule is what makes a task due *without*
> being named. An id matching no task is a named failure (`Task not found: <id>`),
> matching `theteam loop`, rather than a silent `nothing due` that read like "the
> scheduler had nothing for you".

`status`, `tasks`, and `history` are the **machine surface**: their output is a contract with agentic consumers (§3.3) and M6 did not change one byte of it. `watch` reads the same payloads through the same `*_payload` functions; it is a renderer, not a second source.

`--json` is accepted on **either side of the subcommand** for every command. Each subparser declares its own copy with `default=argparse.SUPPRESS`, so the subparser value never clobbers one already parsed from the parent. Until M7 `watch` declared it only on the parent, which made `theteam watch status --json` an argparse usage error; the parser now matches every other command and `cmd_watch` gained the branch that prints the payload the view reads.

`--monitor` turns the watch loop into a change monitor. It reads nothing extra: the loop already re-reads its payload every tick, so the only new datum is the *previous* frame, and the whole feature is a diff between two things the renderer already had. It is a flag, not a new view, and it is off by default — a `watch` without it renders byte-for-byte what it rendered before.

An alert is a **transition, not a level**. The three rules are: a breaker reaching `open`, an audit chain going from `intact: true` to not-intact, and a task leaving the registry. A breaker that is open has been open since the frame it opened; reporting it every tick trains the reader to ignore the line, which makes the surface useless exactly when it matters. For the same reason, a `None` never raises an alert: a task that has never run and a task whose chain was never measured are measurements of absence, not transitions, and reading them as events would be the fabricated opinion §3.3 forbids.

The first frame reports a **baseline**, not "0 changes". It has no previous frame, so nothing has been compared, and a change count of zero there would claim a stability nobody has checked. A change count counts *frames that differed*, not fields — one frame that moved six fields is one change.

The implementation is `theteam/monitor.py`: `diff` and `alerts` are pure, so the rules are testable without a running loop. It imports only the standard library. It is deliberately **not** given an API layer (`get_monitor_status`, `get_recent_events`, `clear_alerts`): those would read a process-local deque from outside the process, which has no caller and would be a second adapter past the payload boundary R1 forbids.

Every command takes an explicit `project_root`. Every command returns a real exit code.

## 2.1 Exit codes and failure shapes

| Code | Meaning |
|---|---|
| `0` | Success. |
| `1` | The command exists and failed. In JSON mode: `{"ok": false, "error": ...}`. In text mode: `theteam <command>: <reason>` on stderr. Never a traceback. |
| `2` | A usage error argparse rejects before the command runs. |

`main()` catches `KeyError`/`ValueError` and bare `Exception`, and `KeyboardInterrupt` returns 1. A `KeyError`'s message is unwrapped from its `repr` so the user sees the cause, not `'x'`.

**One deliberate exception to the 2-for-usage-error rule:** a bare `theteam comment` returns **1**, not 2. Its subparsers are declared `required=False` specifically so the call reaches `cmd_comment`, which prints its own usage error and returns the 1 that this table names for a usage mistake. The parser comment at `cli.py` says so, because the next agent to read it will otherwise "fix" it back to 2.

| Variable | Read by | Effect |
|---|---|---|
| `THETEAM_PROJECT_ROOT` | `build_parser()` | Default for `--project-root`. Falls back to `$PWD`. |
| `THETEAM_METRICS_PORT` | `build_parser()` | Default for `serve --port`. Falls back to `8000`. |
| `THETEAM_TICK_SECONDS` | `build_parser()` | Default for `serve --tick-seconds`. Falls back to `60`. M10 added it with the scheduler. |

## 2.3 One scheduler (M10)

**There is exactly one scheduler in this product, and it is `TaskRepository`
plus `TaskExecutor`.** A task becomes due because `TaskRepository.due()` says
so, and it runs because `TaskExecutor.execute_task()` says so. Nothing else
decides either.

Two schedulers were removed to make that true, and neither was reachable:

| Removed | What it scheduled | Why it was dead |
|---|---|---|
| `core/unified_loop.py` + `core/task_contract.py` | `UnifiedTask` objects added at runtime | Its only producer was `integrated_orchestrator.py`, which had no importer. `theteam serve` constructed the loop and nothing ever called `add_task`, so `/metrics` published `0.0` for every task counter, forever. |
| `routine-engine/` (276 KB, 18 tracked files) | Markdown routine definitions with phases | Zero references from `theteam/`, not in `pyproject.toml`'s `packages.find include`, and no test collected it. It duplicated `theteam/tasks/` function for function: `should_execute` ≈ `due()`, `execute_phase` ≈ `execute_phase`, `safety/rollback.py` ≈ breaker + backup. |

`tasks/scheduler.py` is what remains, and it is deliberately thin: it owns a
clock and nothing else. `run_due_tasks()` is injected by the caller so the
scheduler does not import the CLI. `theteam run` and `theteam serve` call the
**same function**, so a one-shot run and a scheduled tick cannot drift — which
is the entire reason `run_due_tasks()` was extracted out of `cmd_run` rather
than duplicated into `serve`.

The binding to `/metrics` is duck-typed. `MetricsCollector.collect()` reads
`.metrics`, `.tasks`, `.circuit_breaker` and `.health_monitor` off whatever it
is given, so `TaskScheduler` satisfies it with no change to `metrics.py` and no
second mapping of metric names to producers. The parameter is still named
`loop` for the same reason the Prometheus names were never renamed: a scrape is
a wire contract, and renaming a local binding buys nothing.

**A sweep that raises is recorded, not fatal.** `tick()` catches the exception,
stores it in `last_error`, and returns an empty payload, because one unreadable
task file must not take the metrics endpoint down with it. The next successful
sweep clears `last_error` rather than leaving a stale failure.

**`loop` was not renamed.** It schedules one registered task once and prints
`next_run`; it does not iterate, so `routine` would promise a repetition the
command does not perform. `routine` was also already a loaded noun in this repo
(`RoutineScheduler`, `run_routine`, three `routines/*.md`) belonging to a
different data model — markdown phases rather than YAML. If the name ever
reads wrong, `schedule` is the accurate one: it maps 1:1 onto
`TaskRepository.schedule_task`.

### 2.4 Schedule integrity

`task-schedule.json` is the one file in this product that every command writes and
no human reads. That makes it the place where a silent corruption is most likely
and least likely to be noticed, so four properties are enforced rather than assumed.

**Writes are atomic.** `record_run`, `record_skip` and `schedule_task` all funnel
through `_save_schedule`, which writes a temp file and `os.replace`s it. Before
this, three call sites each wrote in place, so a Ctrl-C mid-write left a
truncated JSON file that every later command then refused to parse — the schedule
was destroyed by the act of recording a successful run.

**A corrupt file is moved aside, not raised.** `schedule()` reads through to a
capture point: if the JSON is unparseable the file is renamed to
`task-schedule.json.corrupt-<n>` and an empty schedule is returned with
`last_schedule_error` set. The refusal is reported in the `run` payload rather
than raised, because a schedule nobody can parse must not make every task look
like it is never due.

**An interval shorter than the task is refused.** `schedule_task` refuses an
interval below the task's total worst-case duration (the sum of its phases'
`timeout_seconds`). A 5-minute interval on a 600-second task produces a task that
is permanently overdue: every sweep starts it, the previous one has not finished,
and it never stops running. The guard compares against the same
`worst_case_seconds()` predicate `repair_schedules()` uses, so the write path and
the repair path cannot drift.

**Bad intervals already on disk are repaired.** `repair_schedules()` runs on
every sweep, is idempotent, and reports what it changed. This exists because the
write guard was added after some entries had already been written; a guard that
only applies to future writes leaves the existing damage in place.

**Orphaned schedule entries are purged.** `purge_orphaned_schedules()` removes
entries whose task YAML no longer exists. A schedule entry pointing at a deleted
task is otherwise a permanent, invisible failure: the entry is never due because
the task is gone, and it is never cleaned because nothing reports it missing.

# Part 3 — Trust and Failure Modes

The previous failure in this product was not a crash. It was a system that returned confident output with nothing behind it. Design against that class of failure, not against exceptions.

## 3.1 `theteam status` is the trust surface

```
$ theteam status
project        /your/project
state          /your/project/.omp/theteam
roster         5 members active (architect, pragmatist, skeptic, designer, devops)
tasks          4 registered, 1 scheduled, 0 breaker trips
audit chain    intact, 142 entries (/your/project/.omp/theteam/audit/audit.jsonl)
```

Those are the five lines `status_payload()` builds, and `status` emits them
unchanged. **The session file is not among them**: `status` reads the roster,
the task registry, the schedule, and the audit chain, and nothing else. The
session state is on `theteam comment status`, which reports the `last_digest`
the commentary controller last saw.

When the session file is missing, the controller reports `{spoke: false,
reason: "no_session"}`. It does not fall back to a guess.

## 3.2 Failure modes are named, never swallowed

| Condition | Behaviour |
|---|---|
| No OMP session file | `{spoke: false, reason: "no_session"}` + the path it looked for |
| Session file unreadable or malformed | Raise. Name the file and the line. |
| Session file empty or subagent file | `{spoke: false, reason: "no_session"}`. Never comment on a subagent transcript. |
| Advisory engine errors inside OMP | Propagate. Do not catch and continue. |
| Digest unchanged | `{spoke: false, reason: "no_change"}` |
| Stop signal | `{spoke: false, reason: "stopped"}` |
| Member count exceeds cap | Truncate to the cap, record `truncated: true`. |
| Proposal cannot be written | Raise. Never write a proposal without a proposal file. |
| Task script missing | Rejected at `task create`. Also reported by `run` if it disappeared after creation. |
| Phase exceeds memory bound | Killed, reported with the exit code. Task marked failed. |
| Circuit breaker tripped | Task skipped, reason `breaker_open`, visible in `tasks` and `history`. |
| Audit chain broken | `status` reports it. Writes continue but every entry is marked `chain_broken`. |

## 3.3 The one rule

**No code path returns a synthesized opinion, a default value standing in for a real one, or a placeholder that reads like a result.** This is the `MockAPI` defect, generalised into a constraint the whole system obeys.

The compliance test is: grep the tree for functions that return a plausible-looking value on a failure path. A default is fine when it is a default the user asked for. It is not fine when it looks like a measurement.

# Part 4 — The Advisory Layer

The layer with the least existing code and the most design risk.

## 4.1 One discussion path

The one-shot discussion is `run_discussion()` in `theteam/__init__.py`: the OMP task tool, the
`{id, role, verdict, note}` member contract, the validator, and the synthesis pass. `theteam
discuss` (`cmd_discuss`) is its only caller. **It is not modified by this layer.**

`advisory/commentary.py` is a controller that adds a relevance filter, a cadence, a budget, and
a stop signal on top. It does not reimplement selection, prompting, validation, or synthesis.
Two discussion systems cannot drift because selection and synthesis have one implementation.

> Corrected at M7. This section previously named `advisory/engine.py`, which is not in the tree
> and never was. The guard below is stated against `run_discussion` instead, which is the real
> one-shot path.

## 4.2 When the team speaks, and when it does not

| Trigger | Result |
|---|---|
| Digest changed, or a new user message arrived | Select members, call them, render at most 2 fragments |
| Digest unchanged, no new user message | `{spoke: false, reason: "no_change"}` |
| Latest user message is `stop` / `halt` / `quiet` / `enough` / `that's all` | `{spoke: false, reason: "stopped"}` |
| `.omp/theteam/commentary.stop` exists | `{spoke: false, reason: "stopped"}` |
| Session file missing or is a subagent transcript | `{spoke: false, reason: "no_session"}` |
| More than 4 members selected | Truncate to 4, record `truncated: true` |
| More than 2 opinions produced | Render 2, record `suppressed: N` |

The stop word is matched as the entire leading clause only. "stop the current phase" does not silence the team.

Silence is always reported with a reason. That is what makes silence distinguishable from filler.

## 4.3 Session reading is a file read

The blocking unknown in the previous plan — "does OMP expose a session-history API?" — is resolved by inspection:

```
~/.omp/agent/sessions/<slug>/<timestamp>_<uuid>.jsonl
~/.omp/agent/sessions/<slug>/<timestamp>_<uuid>/__advisor.jsonl   (subagents)
```

The top-level `.jsonl` is the main session. Lines are JSON objects discriminated by `type`. Events of interest:

| `type` | carries |
|---|---|
| `message` | `message.role` ∈ `user` / `assistant` / `toolResult` / `developer`, and `message.content[]` parts of `text` / `toolCall` / `thinking` |
| `custom` | structured payload — 169 events in a live session |
| `custom_message` | rendered note — 31 events |

Measured on a live session: 289 message events, 1.85 MB, roles `{assistant: 204, toolResult: 317, user: 11, developer: 1}`, parts `{thinking: 129, text: 432, toolCall: 318}`.

Three consequences:

1. Reading it is a file read. No new dependency, no API to version.
2. A session directory holds one main file plus a `__advisor.jsonl` per subagent. **The reader must select the top-level `.jsonl` and refuse any file inside a subdirectory.** Otherwise the team comments on a subagent's transcript and presents it as the user's session.
3. **1.85 MB is the entire cost risk.** Reading the file is cheap. Reading its contents into a prompt is not. The reader returns structure, not payload.

## 4.4 `SessionReader` returns four small things

```python
@dataclass
class SessionSlice:
    last_user_messages: list[str]   # last 3 user texts, truncated 400 chars each
    recent_activity: list[str]      # last 8 tool NAMES, never tool results
    touched_paths: list[str]        # file paths from recent toolCall args
    digest: str                     # sha256 over the above
```

Tool **results** are never returned. A `read` result can be an entire file. Tool **names** and the paths they were given are enough to know what kind of work is happening, and cost under 200 tokens for 8 events.

K defaults to 4 messages, hard-capped at 8.

## 4.5 Active member selection, no LLM

The orchestrator picks which roster members speak, capped at **4**, using signals already in hand:

| Signal | Source |
|---|---|
| File extensions in `touched_paths` | `.tsx`/`.css` → Designer; `.py`/`.rs` → DevOps; `.sql` → Architect |
| The latest user message | case-insensitive token match against each member's declared focus |
| The active task's `type` | `analysis` → Architect, Skeptic; `ops` → DevOps |
| Current phase | executing → DevOps; planning → Skeptic |

Selection is deterministic. Zero LLM calls, zero cost, reproducible — the same session state selects the same members, so a test can assert it.

> existed, was tested, and had **no production caller** — `theteam discuss`

## 4.7 Task proposals, never task creation

# Part 5 — Code Structure

## 5.1 Layer contract

Seven layers. Dependencies point downward only. No layer reaches past the one below.

| # | Layer | Owns | Must not know about |
|---|---|---|---|
| 0 | **Entry** | argument parsing, exit codes, JSON output | any domain object |
| 1 | **Control** | tick cadence, pause, idempotency, orchestration order | file formats, subprocesses |
| 2 | **Task** | task schema, validation, persistence, schedule | loops, safety state |
| 3 | **Execution** | running one phase, collecting its result | the schedule, the CLI |
| 4 | **Safety** | bounds, trips, audit, health | task semantics |
| 5 | **Telemetry** | event publication, metrics | who is listening |
| 6 | **Advisory** | roster, selection, discussion, proposals | execution internals |

**The invariant that matters: Layer 3 may not call `subprocess` without a Layer 4 guard in the same call frame.** `AgentIsolation` was built for this and never received a caller. Do not weaken it.

## 5.4 One task format

```

  <id>.yaml                  # canonical. human-editable. version-controlled.
```

`tasks/*.md` and the JSON registry are deleted. The registry survives only as a derived cache under the state directory, never hand-edited, rebuildable from YAML with no information loss.

```yaml
id: system-awareness
name: System Architecture Awareness
order: 3
type: analysis
priority: high
schedule:
  cron: "0 * * * *"
  enabled: true
  retry_on_failure: true
phases:
  - name: inventory
    script: scripts/sa_runner.py
    args: ["--json"]
    timeout_seconds: 120
    memory_limit_mb: 64
outputs:
  - path: .omp/theteam/reports/system-awareness.md
```

`order` replaces `tasks/TASK_ORDER` as a file. `memory_limit_mb` is mandatory per phase — a phase without a bound is rejected at write time, not discovered mid-run.

**Two kinds of phase (M9 Phase 4).** A phase names **exactly one** runner:

```yaml
phases:
  - name: audit
    runner: llm              # a prompt, not a process
    member: architect
    prompt_file: prompts/ground-truth-audit.md
    output: .omp/theteam/reports/ground-truth-audit.md
    memory_limit_mb: 64
```

`script:` runs a Python file inside the bounded container. `runner: llm` hands
`prompt_file` to a named team member and records what it wrote — there is no
container, because there is no process to bound. Both share the executor, the
breaker, and the `ok`/`failed`/`skipped` outcomes.

Three rules, each enforced rather than documented:

1. **Exactly one runner per phase.** Both is ambiguous; neither is a phase that
   reads as "ran, did nothing". `theteam run` refuses either case by name
   (`cli.py:_phase_problem`) instead of passing it on.
2. **A missing provider is a named failure, not a synthesized result.** An
   `llm` phase outside an OMP session fails with
   `llm runner requires an OMP session`, exactly as `run_discussion` does. The
   prompt is real and the member is not; producing something anyway is the
   `MockAPI` defect in a new place. No output file is written.
3. **A test suite stays a `script:` phase.** `native-feature-loop` runs its
   tests through `scripts/run_pytest.py`, not a prompt: a test suite is
   deterministic and must not be judged by a model.

Task **filenames** keep the `task-` prefix the directory already uses
(`repository.py:148`). `tasks/ground-truth-audit.yaml` is invisible to the
registry — not an error, just a file nothing reads — so the shipped tasks are
`tasks/task-ground-truth-audit.yaml` with `id: ground-truth-audit`. The id is
what the command names; the filename is what the reader globs.

**No `depends_on` key.** Three linear tasks a human sequences need no graph, and
a key nothing reads is the schema-lies-nothing-enforces defect that retired
`option_selection_required`.


Validation runs on write. `TaskRepository` rejects a phase without
`memory_limit_mb` at the write that creates it (`tasks/repository.py:72-80`), and
`theteam run` reports a task whose `script` is missing rather than silently
skipping it as a success. The line that said `executor.py:22-24` discovers this
mid-loop named imports, not validation; that pointer was stale.

## 5.6 Per-run context

`theteam run` writes `.omp/theteam/context.md` on every invocation, via
`theteam/core/run_context.py`. It is a few KB of markdown: what ran, what
failed, what needs attention, and the cost of the run.

**Why a file and not more analysis.** The `system-awareness` task already
produced a health score, but it was a 600-second, 384MB phase on a schedule. A
measurement that runs less often than the thing it measures goes stale, and a
stale score is worse than no score because it looks current. Writing a small
context on every run costs milliseconds and cannot go stale between runs.

**It replaced the only other writer of `.loop-state.json`.** `sa_runner.py` wrote
that file from the analysis task. Two writers of one derived file is a race with
a long fuse: the file's contents depend on which task ran last. `run_context.py`
is now the only writer, and `project-integrity` requires the file to exist and to
parse — not to be fresh, because freshness is the property that was removed.


**Emptiness is checked before the always-delivered shortcut.** `run_context` is in
`theteam/advisory/context_slice.py`'s `ALWAYS_DELIVERED`
(`('project_goal', 'project_root', 'run_context')`), so a member receives it even
when the run found nothing. The check that decides whether a section is worth
sending has to run first; otherwise the shortcut ships an empty section to every
member on every tick.

**Delivery is verified, not assumed.** `aggregate_run_context()` reads the file
or reports its absence honestly (`no run context yet`), and
`aggregate_project_context()` includes it under the `run_context` key. A read
failure returns an error section rather than dropping the key, because a silently
missing context section reads as "there was nothing to say".

## 5.7 Not built, and why

Two items are recorded here rather than left as an undocumented gap. Each was
scoped and then deferred; none is started, and none has a partial implementation
to be mistaken for finished work.

**The decision channel (`theteam ask`).** `StateStore.proposals` resolves
`.omp/theteam/proposals/`, and `run_context._open_proposals()` reads it — but
nothing writes a proposal, so the reader always returns empty. Building it means
four coordinated pieces: a `questions` field on the member note schema, a
`needs_decision` phase outcome, a proposal writer, and the CLI surface. The
member-note half is the load-bearing one, because a question that reaches the
parent has to be distinguishable from a member's own reasoning, and the schema
is what makes that distinction durable. Deferred rather than half-built: a
`needs_decision` outcome with no proposal store behind it is a phase that reports
a decision channel exists.

**`write_set` in place of `writable_project`.** Today `writable_project: true`
mounts the whole project writable into the container
(`tasks/executor.py:_writable_mount_args`). The stricter form names the paths a
phase may write and verifies the diff parent-side afterwards. It is the right
design and it is not built. It stays deferred because the guard is only worth
its cost once the manifest is enforced as strictly as the mount is today: a
partial `write_set` that still mounts the tree writable is a second declaration of
intent next to a first, and two declarations of the same permission is how a
permission drifts toward the looser one.

### Guard placement — corrected

The first implementation put the guard at **module scope**, which killed all 28 test files at import time. That was wrong. The requirement is "a caller with no provider raises rather than fabricates" — satisfied by guarding at the point of use.

Correct form, verified live:

```python
def _require_provider():
    if "default_api" not in globals():
        raise ProviderUnavailable(
            "theteam requires an OMP session. Run this inside OMP, "
            "or import it from an OMP-hosted agent."
        )

def run_discussion(project_root, topic):
    """Run a team discussion on a specific topic with actual task spawning."""
    _require_provider()          # first statement, before any orchestration
    ...
```

Two traps this avoids:

1. **Module-scope guard kills the test suite.** 28 files import `theteam` for its safety components (`UnifiedLoop`, `CircuitBreaker`, …), not for discussion. A module-scope raise turns 584 passing tests into 0 collection errors.
2. **Guard must precede config loading.** `run_discussion` calls `load_config` and prints "Failed to load config" before reaching any `default_api` site. A guard placed after config load is inert — the function returns `False` before ever touching the provider.

All five `default_api` call sites live inside `run_discussion`, so one entry guard covers every path.

### Two live defects found while planning

**Members are told they have no tools.** `__init__.py:601-605` reads
`.omp/theteam/tool-manifest.json` and defaults to the literal string `"N/A"`. That file does not
exist — `ls` confirms. Every member prompt therefore carries `## Tool Inventory` / `N/A`. Members

use. A boundary the constrained party cannot see is enforced by luck.

**The full project context is dumped into every member prompt.** `__init__.py:93` does
`yaml.dump(project_context)` per member. For a large project the same tokens are paid N times.
This is the concrete form of "each member means new context, efficiency is critical".

### Prior art: do not reintroduce this

`selector.py:201-207` records a failed design:

> `context` … was tried as a relevance filter and it collapsed the whole differentiation the gate
> exists to check — a project with `database_focus` set and one without both fell back to the same
> member, because the filter ran after selection and overwrote it. A gate that cannot fail is not
> a gate.

**Selection stays deterministic and assertable. The manager may be an LLM; the selector may not.**

### Phase 1 — Wire the selector (do this one first)

Smallest phase, highest value. **1.1** Replace the dead manifest read with the real
`permitted_skills` list, passed into `spawn_member_task` and rendered under the existing
`## Tool Inventory` heading. Signature becomes
`spawn_member_task(member, topic, project_context, permitted_skills)`. **1.2** Replace the
`enabled` filter with `select_members`. The selector takes a `SessionSlice`, not a topic string, so
build a minimal slice from the topic and touched paths rather than adding a fifth signal — adding
one weakens the determinism guarantee the module's docstring names as its entire reason to exist.
**1.3** Respect `MEMBER_CAP`. Truncation is reported, never silent: "5 selected, 4 speak, 1
suppressed". *Gate:* the same topic selects identically twice. If it differs, something LLM-shaped
leaked in.

### Phase 2 — `theteam manager`

`theteam manager --topic "<topic>" | --status | --reset`, `--json` throughout. Reads context
(`analyze_project_context`, already exists), reads the topic, **searches the web**, reasons over
roster + context + results in one LLM call, **asks once** via `ask`, then persists through
`theteam_config.py` — never by hand-editing.

**Roster growth needs two independent triggers.** `analyze_project_context` derives members from
*project* flags (`security_focus`, `database_focus`, …) computed from the repository. A topic about
rate limiting adds nobody; only a project with `infrastructure_focus` does. The requirement is
topic-driven, so the manager adds a member when **either** the project has an uncovered flag **or**
the topic has vocabulary no member's `expertise` covers. Project context alone gives the same team
for every question; topic alone gives a team blind to what the repo contains.

**Do not encode "3 then +4".** The user was explicit that those numbers were an example. A
hardcoded count is the thing not to build. *Gates:* `--status` states why every member is on the
roster; an added member names the topic vocabulary that triggered it — "you might want a database
person" is not a reason.

### Phase 3 — Context efficiency

Slice `project_context` per member by the flag its focus implies. Keep it honest: every fired flag
must reach at least one member, and a flag delivered to nobody is reported, not dropped. Start with
a token match against the `expertise` string; add an explicit mapping only if the match proves
unreliable in testing. **Skipped:** a digest cache for `discuss` — it is a one-shot command with no
repeat ticks, and `commentary.py:223` already covers the case that needs one.

### Phase 4 — Prompt-derived work as registered tasks

```
theteam run --only ground-truth-audit
theteam run --only doc-harmonization
theteam run --only native-feature-loop --topic "..."
```

One new schema field. A phase today runs `script:`; these prompts are instructions to a model:

```yaml
phases:
  - name: audit
    runner: llm
    member: architect
    prompt_file: prompts/ground-truth-audit.md
    memory_limit_mb: 64
```

`runner: llm` and `script:` are mutually exclusive; exactly one must be present. Implementation is
`theteam/tasks/runners/llm.py` exposing `run_llm_phase(task, phase, project_root)`, branched into
`TaskExecutor.execute_task` (`theteam/tasks/executor.py:57`) with the same error handling, the same
`ok`/`failed`/`skipped` outcomes, and the same breaker semantics.

**The missing-script check must not weaken.** `cli.py:243-246` reports a missing script as `skipped`
with a named reason. A phase with *neither* `script` nor `runner: llm` takes that same path —
otherwise the new field is a silent-skip hole, the exact shape §3.3 forbids.

**Three tasks:** `ground-truth-audit` (architect, recon only), `doc-harmonization` (pragmatist,
consumes the audit), `native-feature-loop` (skeptic recon → pragmatist implement → **`script:`
pytest** → doc sync). Tests stay a subprocess: a test suite is deterministic and must not be judged
by a model.

**No `depends_on` key.** `repository.py:26` requires only `id`; nothing reads dependencies. Three
linear tasks a human sequences need no graph. A key nothing reads is the same
schema-lies-nothing-enforces defect as the retired `option_selection_required`.

# Part 7 — Invariants

## 7.1 Product invariants

A user can check every one of these by running a command.

1. `theteam status` on a bootstrapped project shows a roster, the state directory, task counts, and an audit chain that reads `intact` or names its absence. It reports no session.
2. `theteam discuss` outside OMP fails with the exact command to run inside OMP, and returns no opinion.
3. Two bootstraps of structurally different projects produce different rosters.
4. `theteam run` with nothing due returns `{ran: 0}` and runs nothing. Two consecutive calls are identical.
5. A task failing 5 times trips a breaker, visible in `theteam tasks` and `theteam history`.
6. A phase over its memory bound is killed and reported, never left running.
7. `theteam history` shows per-task success rate, last run, last failure.
8. Every tick reports `spoke: true` with at most 2 fragments, or `spoke: false` with a reason.
9. `theteam watch status --once` on a project with no audit chain and no run tasks shows `absent` / `never run`, and never prints `closed`, `intact`, or `0%` for anything it did not measure.

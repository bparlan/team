Shape is sound. The citations were never right. Every architectural relationship the diagrams assert — all 13 edges — is real and verified against the source. Every module ARCHITECTURE.md assigns exists, and all 20 core/ modules have a live or correctly-documented importer story.
The decisive measurement: scripts/update_team_check.py compares each cited file against the sha256 recorded in active-usage-architecture.anchors.json. Thirteen of fourteen cited files are byte-identical to when the anchors were recorded at ca3673b. An unchanged file cannot have moved its line numbers — so those nine citations were pointing at the wrong line the day they were written. This is an authoring defect, not staleness, and it needs a different fix than staleness does.

1. Method

Three independent measurements, so the numbers are comparable to ARCHITECTURE.md §5.2.1's own claim of having used "an AST scan for imports at any nesting level plus a runtime sys.modules check across all three entry points."

  • AST import scan — 97 modules, 155 in-package edges, imports at any nesting level.
  • Runtime sys.modules — what import theteam actually loads, plus every lazy re-export resolved.
  • Symbol resolution, historical — each cited file:line resolved against the real def/class line at the revision the anchors were recorded, and again at HEAD, so authoring defects are separated from staleness.

The architecture gate was run, not assumed: bash scripts/check_invariants.sh → PASSED (7 checks). scripts/check_import_graph.py → 88 modules (budget 90), 7 of 7 theteam.core.* (budget 8), no cluster tier. Suite: 800 passed.

Nine of thirteen citations were wrong the moment they were written.
The proof: scripts/update_team_check.py reports that thirteen of the fourteen cited files are byte-identical to their recorded sha256. Independently confirmed with git diff ca3673b HEAD -- <file>, which is empty for all thirteen. A file that has not changed cannot have moved a line number. Directly settled: git show ca3673bf:theteam/cli.py | grep -n '^def build_parser' prints 1203, not 604. So theteam_cli cited the wrong line at authoring, and has cited it ever since.

This is not the drift the anchors mechanism was built to catch, and that distinction decides the fix. Staleness is fixed by re-deriving; an authoring defect is fixed by correcting the number, and re-deriving would reproduce the same wrong answer as long as the generator resolves lines the same way.

Every wrong citation points at the file's line 1 or into its header comment. agent_isolation:1, circuit_breaker:1, team_manager:1 — all cite line 1. llm.py:82, context_slice.py:90, executor.py:57 land inside module docstrings. A plausible-looking line inside a docstring is a citation that resolves to nothing.
Likely cause [INFERENCE]: whoever derived the diagram recorded the line where a symbol became mentionable — the module header or the docstring naming it — rather than the line of its def. Nothing checked, because a line inside a file that exists looks correct at a glance and to grep. A checker that resolves the named symbol rather than testing that the line is non-empty would have failed all nine at authoring time.

3. The anchor mechanism — real, working, and blind to the actual defect

The gate exists and works. My first pass missed it. scripts/update_team_check.py is the staleness gate for exactly this diagram. Run it: python3 scripts/update_team_check.py → exit 3, verdict re-derive may be needed, and it names one changed file: theteam/SKILL.md. That is correct — SKILL.md is the only cited file whose content changed, and it is the one node whose citation is genuine managed staleness (:117 pointed at roster prose then, and at the spawn-loop section now).
But it hashes whole files, so it is structurally incapable of detecting the nine authoring defects. _hash() is sha256(bytes)[:16] — a change detector, not a citation checker. It answers "did this file change?" and never "does line 604 hold build_parser?". Thirteen unchanged files producing nine wrong citations is exactly the case it cannot see.
Correction to an earlier reading: I first compared anchors with git hash-object and concluded 14/14 had drifted. That was my error — a different hash function on the same bytes. Recomputed with the gate's own sha256[:16], 13/14 match. The only drifted anchor is SKILL.md, and the gate reports precisely that.
And the gate stops after the first diagram. check() returns at update_team_check.py:176, inside the loop over DIAGRAM_DIR.glob("*.json"). sorted() puts active-usage-architecture.json first, so it is evaluated and then the function returns — active-usage-milestones.json and llm-phase-spawn.architecture.json are never checked at all. _report() also writes one fixed filename (.omp/theteam/reports/update-team.md), so even if the loop ran, each diagram would overwrite the last.
Why it went unnoticed: only one of the three diagrams has a .anchors.json sidecar, and the two without one continue past before the return — milestones and llm-phase-spawn would be skipped anyway. So the bug is currently masked by the absence of the very inputs that would expose it. Recording a second sidecar is what would surface it.

4. Where the code contradicts the document

4.1 Layer 0 contract is violated by the CLI — defect

ARCHITECTURE.md:459 defines Layer 0 (Entry) as owning "argument parsing, exit codes, JSON output" and requiring it "must not know about any domain object."

theteam/cli.py references six domain symbols directly: TaskRepository, TaskExecutor, TaskScheduler, StateStore, CircuitBreaker, run_discussion.

Reason — the doc describes an intent that was never completed. §2.3 shows the pattern being applied where it mattered: run_due_tasks() was "extracted out of cmd_run rather than duplicated into serve" precisely so the scheduler would not import the CLI. The same discipline was never applied to the other 11 commands. Layer 0 is an aspiration in §5.1 and a description of practice nowhere else. This is the same class as the health_monitor.py finding at §5.2.1 — documented honestly, but recorded as "open work" rather than as a contract breach.

4.2 import theteam contradicts its own comment — stale

theteam/__init__.py:30-33 states that importing theteam.core.state_manager "loads database, which loads the PostgreSQL cluster/wal/transaction modules", so every import theteam pulled a database tier §5.1 never placed in the stack.

Measured sys.modules after a bare import theteam: database is loaded — but postgres_cluster is not. The chain stops one link short of what the comment claims.

Reason: database.py now imports postgres_cluster at point of use rather than module scope — which is exactly the fix §5.2.1 describes ("Imported at point of use by database.py"). The comment documenting the defect was never updated to record that the defect is fixed. The comment is correct about the past and wrong about the present, and it is the first thing a reader meets when reasoning about the import graph.

4.3 Two packages are empty on disk and untracked — residue

theteam/skill/ and theteam/automation/ exist as empty directories. git ls-files returns nothing for either — git cannot track an empty directory, so they are not in the commit at all. They are local residue from skill/SKILL_metadata.py, deleted in M10, plus an automation/ of unclear origin.

Neither is named in §5.2, and §5.3.1's table records one orphaned directory (config/routine-engine/) as "not removed, with the reason". These two have no entry because they cannot have one: nothing is tracked.

Reason, and why it matters more than it looks: the residue is invisible to every tool that reads the repo — git ls-files, the AST scan, the packaging config — so it will never appear in a diff, a review, or a clone. It survives only on this machine. That is the cheapest possible form of the drift §5.3.1 exists to prevent, and the fix is rmdir. Listed last in priority for exactly that reason: it is real, and it is nearly free.

7. Report surface

run_discussion writes {conversation_id}-discussion-report.md into .omp/theteam/reports/ (__init__.py:513,947-950; SKILL.md:351 repeats it).

That is the most user-facing artifact the product produces, in Markdown, into a dot-directory. Meanwhile the tracked human surface reports/ holds 2 HTML and 8 Markdown files. One of the two HTML files is this report.

reports/.handoff/ holds exactly one file, root-organization-scan.md — and it is not one of the 8. It is a separate machine handoff already placed there; the plan's p2 move has not happened. All 8 of the reports/*.md files are tracked and clean (git ls-files: 8/8; git status --short reports/*.md: empty), so they are committed and unmodified — clean status here means already committed, not never moved. That is the whole gap: they were committed into the human surface as Markdown, and no check inspects the filesystem to object.

The rule is real and enforced: scripts/check_task_contract.py:41,224-233 check 5 states "reports/ is written only by a task's final phase, and only as HTML". But its scope is task-declared outputs — it validates output: fields in tasks/*.yaml. It does not inspect the filesystem, so hand-placed Markdown in reports/ is invisible to it. Those 8 files pass because nothing asks about them.

This is exactly the human-report-surface.yaml plan in archive/tasks/, already written and waiting. p2 of that plan is the 15-minute phase that moves them.

The pattern across every finding is the same: a measurement was taken correctly, written down, and then nothing kept it current. §5.2.1 knows event_bus and health_monitor have no importer. __init__.py knows the import chain changed. ARCHITECTURE.md:12-32 knows the milestone pair is out of sync. The knowledge is in the repo. The enforcement is not.
The diagram case is the sharpest version, because the enforcement mechanism exists and runs — it is simply answering a different question. Whole-file hashes answer "did this file change?"; the defect is "does line 604 hold build_parser?" Nine wrong citations sat inside files that never changed, behind a green gate. That is worse than no gate, because it converts an open question into a false all-clear. The fix is narrow: resolve the named symbol at the cited line, which is what scripts/check_prompt_truth.py already does for prompts — the mechanism exists in the repo, on a different surface.
